## Problem

The CSI controller is a Deployments pod. If it dies mid-operation (while waiting for a TrueNAS job, mid-provisioning, mid-delete), the operation is abandoned. No cleanup happens — the volume exists on TrueNAS in a half-created state (e.g. a sparse zvol created but no NFS share or iSCSI extent linked yet), the CSI controller never finishes the call, and kubelet retries indefinitely.

Dell handles this with a Podmon sidecar that monitors pod health and calls `NodeUnpublishVolume`, `NodeUnstageVolume`, or `ControllerUnpublishVolume` on the local CSI socket when it detects the primary pod died unexpectedly. Our controller has no such mechanism.

## Design

A Podmon sidecar deployed alongside the TrueNAS CSI controller (and also alongside the node plugin, see issue #3).

### How Podmon works (adapted from Dell's model)

Podmon runs as a sidecar in the CSI controller pod. It has a unix socket connection to the companion CSI driver on the same node.

1. Podmon watches the companion pod's health (via kubelet's readiness probes and LivenessProbe).
2. When the companion pod becomes unresponsive (LivenessProbe fails and Podmon is still running), Podmon makes gRPC calls through the unix socket:
   - `NodeGetInfo` (node-side Podmon, in the node plugin)
   - `ValidateVolumeHostConnectivity` — our health check from issue #1 (node-side)
3. If the companion pod crashes, Kubernetes restarts it and Podmon's job is done — the restarted pod will finish any pending operations.
4. If the companion pod's Pod is deleted (evicted, OOMKilled, manually removed), Podmon is also deleted. But the orphan volume remains on TrueNAS.

### Orphan reconciler (complementary to Podmon)

The Podmon sidecar also runs an orphan reconciler in the controller:

- Calls `pool.dataset.query` to list all datasets with the ownership marker
- Compares against in-cluster CSI volumes (PV/PVC state)
- For volumes existing on TrueNAS with no PV: logs the discrepancy and optionally cleans up (with a configurable policy — don't delete volumes that were provisioned by a crashed controller if the operator wants to investigate)
- Periodic: every 60 seconds

### Why a sidecar matters

Dell's Podmon sidecar also handles node failure. If the node plugin's pod dies mid-operation, Podmon on the node side calls `NodeUnstageVolume` and `NodeUnpublishVolume` on the same unix socket, cleaning up the mount/device so the operator can safely remediate.

Our node plugin already has `NodeUnstageVolume` as part of its implementation. Podmon would be a safety net that calls it when the node plugin's pod is unexpectedly removed.

## Acceptance Criteria

- [ ] `TestPodmonDetectsUnresponsiveCompanion`: when the companion CSI driver stops answering gRPC on the unix socket, Podmon attempts cleanup calls
- [ ] `TestOrphanReconcilerDetectsUnlinkedVolume`: a dataset exists on TrueNAS with the ownership marker but no corresponding PV -> reconciler detects it
- [ ] `TestOrphanReconcilerSkipsLocalVolumes`: a dataset exists on TrueNAS AND has a corresponding PV -> reconciler does not touch it
- [ ] `TestPodmonStaysAliveWhenCompanionRestarts`: Podmon survives the CSI driver's LivenessProbe and restart cycle
- [ ] `TestOrphanReconcilerPeriodicCleanup`: every 60s, the reconciler queries TrueNAS and reports discrepancies
- [ ] Integration: deploy the driver with Podmon, kill the controller pod; assert Podmon detects the failure and the restarted pod resumes cleanly
